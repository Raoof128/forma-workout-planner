# Backend-equivalent data-layer audit

Date: 12 October 2026 (Australia/Sydney). Scope: the complete authored persistence, validation, import/recovery, and workout business logic in FORMA.

## Scope and method

There is **no server backend** in this repository: no HTTP API, authentication system, remote database, or server jobs. The audit therefore examined the browser data layer and every component that changes or derives training data. Creating remote services would change the user's chosen browser-local product scope and was not part of this pass.

Reviewed source file by file, traced read/write and error paths, checked the existing regression suite, introduced isolated failure/concurrency tests, and exercised the integration in Chromium and Firefox. Generated dependency code and binary assets were not audited line by line. This is a source and behavior audit, not a penetration test or a guarantee that every possible defect has been eliminated.

## Findings and remediation

| ID  | Impact          | Finding                                                                                                                                                    | Resolution and evidence                                                                                                                                                                                                    |
| --- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D01 | High            | A present but rejecting Web Locks API could reject initialization without a handled fallback or lose the attempted edit.                                   | The repository distinguishes lock acquisition failure from mutation failure, enters temporary mode, and retains a valid edit once. Unit and browser tests simulate rejection.                                              |
| D02 | High            | Temporary edits did not advance the workspace revision, so restore confirmation could miss intervening in-memory changes.                                  | Every acknowledged mutation advances revision, including temporary edits. A stale restore is rejected without replacing memory.                                                                                            |
| D03 | High            | Restore preserved only disk contents and could discard distinct, unsaved temporary changes.                                                                | Preserve both distinct originals before replacement. If either preservation write fails, the workspace is not replaced. Unit and browser tests inspect recovery copies.                                                    |
| D04 | High            | Corrupt-data recovery had no check that another tab had already replaced the original while recovery waited.                                               | Compare the exact raw original inside the lock; reject stale recovery and load the latest state.                                                                                                                           |
| D05 | Medium          | Recovery keys used only millisecond timestamps, allowing collisions.                                                                                       | Add a random ID to each key; test consecutive restores at the same mocked time.                                                                                                                                            |
| D06 | Medium          | A storage read failure while on the recovery screen could leave a null workspace paired with a normal temporary-mode screen.                               | Retain the invalid-data state and raw original when access is lost.                                                                                                                                                        |
| D07 | Medium          | Validation admitted history with zero completed sets and an active ID already present in history. These could inflate workout counts or prevent finishing. | Reject both states at the shared validation boundary; leave invalid stored input available for recovery.                                                                                                                   |
| D08 | Medium          | Unbounded timestamps and durations could enter timer/display arithmetic.                                                                                   | Bound Unix timestamps to JavaScript's valid date range and duration to the safe-integer range. Clamp paused remaining time to the supported 600-second maximum.                                                            |
| D09 | Medium          | Import size enforcement was duplicated in UI handlers and absent from raw saved-JSON parsing.                                                              | Centralize file reading and UTF-8 byte-size checks with a 20 MiB limit before parsing. Retain malformed/oversized stored content rather than replacing it.                                                                 |
| D10 | Medium          | Starting an already-open routine detail could silently use prescriptions changed in another tab.                                                           | Compare the selected routine with the latest definition inside the mutation; show a reopen message on conflict.                                                                                                            |
| D11 | Medium          | Temporary-mode routine/workout creation still depended on `crypto.randomUUID`, unavailable on some HTTP origins.                                           | Use a UUID v4 fallback based on `crypto.getRandomValues`; test routine and session creation without the secure-context APIs.                                                                                               |
| D12 | Medium          | The schema accepted fractional weights such as 22.25 kg, but routine/history forms rejected them through half-kilogram step restrictions.                  | Align weight input steps with the numeric data contract; browser tests preserve fractional values through edits.                                                                                                           |
| D13 | Maintainability | Persistence, React state, locks, and recovery were intertwined, making exceptional paths hard to test.                                                     | Extract `src/persistence.js` with injected read/write/lock/clock/ID adapters. React now subscribes via `useSyncExternalStore`; mutation drafts are cloned so rejected updaters cannot partially alter acknowledged memory. |
| D14 | Maintainability | Runtime requirements and data-layer checks were undocumented.                                                                                              | Declare the Node.js engine, add separate unit/browser scripts, and document architecture, compatibility, deployment, and contributor expectations.                                                                         |

### Cross-tab finding discovered during final verification

The Firefox concurrent-edit regression intermittently lost a note while another tab saved a profile (also reproduced in 1 of 15 isolated repetitions before remediation). The repository now yields a task boundary after acquiring the lock and after the synchronous mutation, before releasing it. This addresses storage implementations with task-local read snapshots and delayed write checkpoints; Mozilla documents this behavior in its [localStorage concurrency discussion](https://bugzilla.mozilla.org/show_bug.cgi?id=1740144). A deterministic snapshot adapter test and repeated simultaneous browser edits exercise this boundary. The browser-level cause is inferred from the failure pattern and storage semantics; it was not diagnosed inside Firefox itself.

## Compatibility and operational limits

Version 1 remains the backup format. Missing legacy default fields still load. Logically inconsistent history, invalid timestamps, or oversized data now enters the existing non-destructive recovery path rather than being accepted. Raw original data can still be downloaded.

Persistence remains bound to the browser origin and available local quota. Web Locks coordinate cooperative tabs; they cannot prevent arbitrary scripts or extensions from modifying localStorage. Recovery uses multiple individual atomic writes, not a crash-atomic multi-key database transaction. Recovery copies have no automatic cleanup policy and consume quota. Back up externally before clearing site data.

Production dependency audit (`npm audit --omit=dev`) reported **zero known advisories** on the audit date; that result does not establish that dependencies contain no defects. Safari, physical mobile devices, and assistive technologies were not newly verified in this pass.
