# Performance measurements

The final samples below use application source `cc771830b92929485dae5f4fe8297a49df9fa394`. Later report-only changes preserve the same application/test/configuration fingerprint.

The final local guest build passes. Its main JavaScript grows by 2,229 bytes, and the existing large-chunk warning remains. The paired samples do not establish a load-time improvement. Throttled mobile LCP remains about 3.9 seconds and is an outstanding performance concern.

## Reproducible method

The [measurement harness](harness/measure-performance.mjs) accepts loopback origins only. It ran the frozen `3c27308` build and final build in 20 fresh Chromium contexts: five before/after pairs for each profile, with alternating phase order. Desktop uses 1536 × 1024 and normal CPU; mobile uses 390 × 844, 4× CPU throttling, 150 ms network latency, 200,000 bytes/s download and 93,750 bytes/s upload. Cache is disabled. Both phases use the same pinned Chromium, local fonts, reduced-motion preference and journey: overview, routine, start workout, edit weight and complete a set. No other browser suite ran during measurement.

Paint, layout-shift, long-task and Event Timing observers run before navigation. The cold snapshot waits for a real LCP candidate, fonts and visible image decoding. Trusted click-to-two-animation-frame samples cover the journey. CDP provides resource/runtime measurements. [Raw production samples](evidence/PERFORMANCE_PRODUCTION.json) and [exact bundle bytes](evidence/BUILD_SIZES.json) remain available.

These are local lab observations, not field p75 Core Web Vitals, a physical phone, Lighthouse scores or field INP. The ready timestamp includes observer delivery and image/font waits; it is not TTI. Shift totals describe this captured journey, not a site-wide CLS certification. Heap samples do not establish leak freedom.

## Production lab results

Each value is the median of five samples. Timing ranges overlap substantially, and these changes are primarily correctness and accessibility fixes. No causal speedup is claimed.

| LCP, ms                                      |            168 |           164 |             3,920 |            3,920 |
| Cold layout shifts without recent input, sum |              0 |             0 |                 0 |                0 |
| Cold long tasks, total ms                    |              0 |             0 |               346 |              335 |
| Resource transfer, bytes                     |        887,953 |       888,758 |           639,833 |          640,638 |
| Largest sampled click-to-two-frame delay, ms |           57.4 |          56.4 |              56.6 |             57.3 |

Desktop LCP samples span 160–552 ms before and 160–224 ms after. Mobile spans 3,908–3,972 ms before and 3,912–3,928 ms after. All 20 journeys completed without recorded browser errors or unexpected external requests. The mobile payload and parse cost remain a priority for a separately measured optimisation.

## React profiling

A temporary response interception wraps the development root in `React.Profiler`, preserving Strict Mode, error boundary and account provider. It changes no product file and is removed when the fresh context closes. Three interleaved before/after pairs use a synthetic 2,000-session history, a running workout, a three-second idle window, set editing/completion and Progress navigation. All six profiles returned 26 commits each with no browser errors. See [raw React samples](evidence/PERFORMANCE_REACT.json).

| Stage                   | Before median summed render duration, ms | After median summed render duration, ms |
| ----------------------- | ---------------------------------------: | --------------------------------------: |
| Mount                   |                                     81.4 |                                    80.1 |
| Three-second idle timer |                                    130.3 |                                   122.5 |
| Edit and complete       |                                     39.7 |                                    39.1 |
| Progress navigation     |                                     19.1 |                                    19.6 |

Stage commit counts vary at timer boundaries; these are summed render durations per window, not individual component latency or production frame time. Development profiling and Strict Mode add overhead. These small samples support neither a rendering speedup nor a demonstrated new performance regression.

## Retained unsuccessful measurement attempts

The first 12 production journeys completed, but some desktop snapshots preceded LCP observer delivery. They are not used as zero-LCP results. The first React attempt profiled the baseline and then correctly failed on zero final samples: the interception did not match Vite's HMR timestamp query. The final harness matches that query and requires nonempty samples. Both earlier receipts remain private; their dispositions are recorded in the verification evidence. A later complete 20-production/six-React set taken before the final narrow Security/tablet CSS corrections was also superseded by the final frozen-source set above. A second complete set before the final Skip callback was also superseded. Final selection follows the application source version, not the most favourable timing; medians in the final mobile set are equal. No sample was invented or selectively relabelled as a pass.

The host has 8 GiB RAM. Earlier concurrent browsers and low disk produced severe contention and timeouts. Only reconstructible audit-owned compiler/index caches and duplicate frozen public assets were reclaimed; source, signed products and evidence were retained. Final measurement ran separately from browser matrices.

Versions: Node 24.21.0, npm 11.19.0, React 19.3.1, Vite 8.3.5, Motion 14.6.0, Playwright 1.64.1 and its pinned Chromium. The exact production Node 26.12.1 runtime was not installed. Field CWV, energy, thermal behaviour and physical Safari remain unverified. Method references: [React Profiler](https://react.dev/reference/react/Profiler), [Web Vitals](https://web.dev/articles/vitals) and [Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference).
